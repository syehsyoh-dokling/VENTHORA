# QA report, 15–16 November 2026

Two independent reviews of the source (code quality; security and scale against what a bank's vendor review asks),
a static check of every dashboard call against the declared routes, a sweep of every GET endpoint, a walk through
the menus, and the sponsor connections on the live staging server. Findings were made by reading the code and by
running the checks named below; nothing here is a certification.

## Findings that were fixed

**Money and approvals**

| Finding | Fix |
|---|---|
| `POST /v1/executions` (and `/autonomous`, `/resume`) ran a plan for any signed-in person, on a policy the caller wrote | Only a finance role runs a plan; the reserve floor is never below the FCO's mandate; resume asks the writer gate |
| Approval endpoints took the acting role and name from the body of the request (period close, book adjustment, budget grant, payee verify / call-back / suspend / reinstate, intake review, DoA run, live step) | With sign-in on, the signed-in person's own name and role replace them |
| A forwarded "approval" that was in fact a refusal ("not yet approved", "I can't approve this", a question, a line the FCO only quoted) approved an advance | Only the FCO's own words count, and a sentence that takes the approval back approves nothing |
| "USD 1,500" in an advance email was read as 1.5 | One amount reader for every email that asks for money |
| The 23:59 run could fund the card account more than once for one advance | The funding is kept on the request before the card is made; a retry finds it; one request id per funding round; a failed return is on the audit chain |
| A winner's invoice that differed from its purchase order could be paid on arrival before it was held | It is held inside the intake, before anything is published or paid |
| A person could approve and award their own purchase request when it was raised by email | One same-person rule for every decision |
| The agent awarded on a single quotation | Fewer than three quotations go to a person |
| A server could take another server's expired lease simply by paying | Paying keeps only a server's own lease; another server's is taken only by a takeover. Reading the status changes nothing |
| Manual transfers, wallet payouts, advance cards and resume did not ask the writer gate | They do |
| Two processes on one database could both claim the same payout | The write lock is taken before the read |

**Hardening**

| Finding | Fix |
|---|---|
| The rate limit trusted the first `X-Forwarded-For` hop, which the caller writes | A direct caller is its socket address; behind a local proxy the last hop is used |
| Security headers and the rate limit did not cover the 401 / 403 answers of the sign-in and access middlewares | The hardening middleware is now the outermost |
| The Docker image copied the local `data/` directory, stores and secrets included | `.dockerignore` keeps every store, tenant directory, run and `.env` out of the image |
| The winner's form link never expired | 30 days |
| Reference numbers were read out of ordinary sentences ("TA/DA", "PR-team", "ref # 555-1234") | A number needs its label and a digit; dates and amounts are not numbers |
| The model was asked every minute about a request for quotation a person had already been told about | Asked again only when a quotation changed |

**Closed on 16 November, after the first version of this report**

| Finding | Fix |
|---|---|
| A self-hosted VENTHORA without sign-in was an open super-admin API | Without sign-in it answers its own machine only; from elsewhere it is refused unless sign-in is turned on or the operator opens it knowingly (`VENTHORA_OPEN=1`) |
| No guard on the addresses a person types for a connector or a discovery | Link-local addresses (the cloud metadata service) are always refused; on a multi-company deployment loopback and private networks too; redirects are no longer followed |
| Every currency was assumed to have two decimals | One ISO 4217 table decides: no decimals (JPY, KRW, VND ...) means whole units, three-decimal currencies (BHD, KWD ...) are kept to two of their three, units of account are refused |
| A requester could read what other people earn and may approve | The people list a requester gets carries names, roles and units only |
| An advance approved on the dashboard was not allocated | One with no bank account of its own is allocated and paid at 23:59 like one approved by email; one with its own account stays a person's choice |
| Two modules and thirteen functions or constants that nothing used | Removed, each after a whole-word search across the source, the tests, the scripts and the dashboard |
| The test log was flooded by the mail provider's delivery notices and said "action" for the new steps | Delivery notices are not recorded; the new steps have their own sentence; a card link's token is never written |
| A notification crashed in the browser for an email that became a request | Fixed; such an email is FILED in Intake under its number instead of waiting for a payment review |

## Findings that are open

Stated plainly, most important first.

1. **Read authorization by role is partial.** A requester no longer sees pay and limits, but any signed-in person can
   still read the audit log and most lists. Only the Developer role is kept out of FCO Authorize.
2. **Inbound email authentication** accepts an `Authentication-Results` header without checking who added it. It is
   safe only where the receiving mail service strips the sender's own.
3. **Secrets are plain text in SQLite** (bank keys, SMTP password, connector and TOTP secrets). No KMS.
4. **The audit chain is unkeyed.** It shows a change made by someone who cannot recompute the chain; whoever can
   write the file can. Anchoring on Alta is the answer and is not connected on the live server.
5. **One platform token** is shared by every company's process and signs the platform's own cookie.
6. **A forwarded approval is still a typed text.** It is read strictly, the FCO is told at once and can cancel until
   23:59, but nothing proves the FCO wrote it. A mail service that signs what it forwards would.
7. **Scale.** One process per company, SQLite, synchronous store calls inside async handlers, whole collections
   loaded per request, one lock for every execution. An estimate from the code, not a measurement: tens of
   concurrent users and low hundreds of payments a day per company. A second instance is not supported: the rate
   limiter, the lockout counter and the caches are in memory, and only the payment paths ask the writer lease.
8. **Complexity.** The ten most complex functions (the gateway's `create_app`, the intake's `ingest`) are far above
   what a reviewer accepts, and `api.py` is one file of about eleven thousand lines.
9. **Not done at all**: an external penetration test, dependency and static-analysis scanning in CI, a lockfile,
   data retention and deletion, operating-system isolation between companies, a rehearsed standby.
